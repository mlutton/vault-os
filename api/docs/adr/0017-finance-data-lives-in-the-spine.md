# Finance's data, migrations, and matching engine live in Vault-Os-Api, not Fable-Os-Web

The Finance tab handoff (`Personal-OS/personal-os/projects/finance-build-out/V-OS redesign directions/design_handoff_finance/README.md`) specs a five-screen personal-finance ledger: accounts, a hand-kept spending plan, imported bank statements, a transaction-matching engine, and a 30-day cash-flow projection. Its data model section says "SQLite via existing `lib/` patterns" — but `Fable-Os-Web` has no database at all (it's 100% file-based against `VAULT_ROOT`; see its own `CLAUDE.md`), so that phrase pointed at nothing that actually exists.

Decided: Finance's schema, migrations, money-math (integer-cents arithmetic, dedupe hashing, processed/overdue projection logic), and auto-matching engine are built in `Vault-Os-Api`, extending its existing SQLite layer (`vaultos/db/conn.py`'s numbered-migration + `PRAGMA user_version` pattern) and tested with this repo's existing `pytest` suite. `Fable-Os-Web`'s `/finance` route becomes a thin client — five screens rendering data fetched through new endpoints, following the same shape `lib/spineClient.ts` already uses for everything else this app reads from the spine (typed per-endpoint fetchers, snake_case-to-camelCase translation, no business logic on the client side). New endpoints stay granular, one (or a few) per screen/concern rather than one large `/finance/state` blob, matching ADR-0004's "keep `/state` thin" precedent.

## Considered Options

- **A new local SQLite file added directly inside `Fable-Os-Web`** (new `better-sqlite3`-style dependency, a brand-new `lib/db.ts`-style module, all Finance logic living in the Next.js app). Matches the handoff doc's literal "local-first" framing most directly, but builds a whole second, parallel data-layer pattern in a repo that has never had one — and this app is explicitly slated to retire once `Vault-Os-Api` / a future `Vault-Os-Web` reach parity (see the workspace root `CLAUDE.md`'s Direction section). Rejected — the user's explicit call.
- **Plain JSON/CSV files under `VAULT_ROOT`**, matching `Fable-Os-Web`'s actual current architecture (everything else there is files, not a database). Rejected: the matching engine (fuzzy merchant resemblance, first-match-wins rule priority) and the category/plan-vs-actual rollups need real relational queries; forcing that logic onto flat files fights the shape of the problem for no benefit, since this repo already has a working SQL layer.

## Consequences

- CSV import is a spine-side concern too (see the map for the Finance build, `#1`): the raw file uploads to a new `Vault-Os-Api` endpoint and is parsed server-side, rather than `Fable-Os-Web` parsing it client-side and posting structured rows. `Vault-Os-Api` has no existing multipart/`UploadFile` precedent — this is new, if straightforward, ground for it.
- The handoff doc's own "Build order" (data model → plan → cash flow → accounts/import → ledger/matching → categories/recurring) still holds as a dependency order, but phase 1 (data model + the money-math/matching logic the doc calls `lib/finance.ts`) is now Python in this repo, pytest-tested, not a TypeScript module in `Fable-Os-Web` under `npm test`'s `tsx`-script convention.
- `Vault-Os-Api`'s own tracker convention still applies: this ADR is the design record; the wayfinder map and its tickets stay ticket-sized, referencing this file rather than restating it.

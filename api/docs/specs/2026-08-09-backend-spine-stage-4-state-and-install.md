# Backend Spine — Stage 4: Composite `/state` and systemd Install

**Date:** 2026-08-09
**Status:** Ready for implementation
**Scope:** Stage 4 of sub-project 1 (per `docs/specs/2026-08-09-backend-spine-design.md` §10): `GET /state`, plus extending `/daily`, `/runs`, `/jobs`, `/runner` with fields the composite needs, plus the `vaultos-api.service` systemd unit. Produced via a `/grill-with-docs` session (see `docs/adr/0004-state-uses-spine-shape-not-vaultstate-parity.md` and the updated §5/§9 of the design spec) rather than `superpowers:brainstorming`.

Depends on Stage 3 being complete — it is, merged to `main` at `09c3d98`.

## Problem Statement

Stages 1-3 gave the spine a write path, a history path, and pure-read endpoints for skills, runner, metrics, daily notes, and integrations — but nothing that powers the HUD's full cockpit view in one call, and no way to run the spine as a persistent service rather than a foreground `uvicorn --reload`. Concretely: (1) the HUD's `VaultState` shape pulls together nine different data sources, four of which (a channel's latest video, today's morning report headlines, per-skill duration estimates, today's lane-brief headlines) have no spine-side reader at all yet; (2) three existing endpoints (`/daily`, `/runs`/`/jobs`, `/runner`) are each missing at least one field the HUD actually renders; (3) there is no systemd unit, so the spine only runs when someone remembers to start it by hand.

## Solution

Add four new pure-read functions (latest video, morning report, skill ETAs, lane briefs), extend four existing endpoints at the source with their missing fields, add one new composite `GET /state` endpoint that assembles all of it using the spine's own snake_case shape (not a `VaultState`-parity clone — see ADR-0004), and add a `systemd --user` unit for persistent, boot-surviving operation.

## User Stories

1. As the HUD, I want one endpoint that returns everything the cockpit view needs, so I don't have to make nine separate calls on every poll.
2. As a developer, I want `/state`'s JSON to use the spine's normal snake_case convention, so it's not the one endpoint in the API that breaks the pattern (ADR-0004).
3. As a developer maintaining sub-project 2 later, I want `/state`'s shape to be internally consistent and complete rather than a byte-for-byte `VaultState` clone, so the translation layer I write there has one clear source to translate from.
4. As the HUD, I want the currently-airing/latest YouTube video's title, URL, view/like/comment counts, and publish timestamp, so the cockpit can show what's live without a separate call.
5. As a user, when no `latest-video.json` exists yet, I want that field to come back `null` rather than an error, so a channel with no video data yet doesn't break the whole composite.
6. As the HUD, I want today's morning report's headline bullets (with each headline's first source link, when present), so the AI Wire panel has something to show without re-parsing markdown client-side.
7. As a user, when today's morning report hasn't run yet, I want `morning` to come back `null`, not an error.
8. As the HUD, I want today's lane-brief documents (Leadership, Payments, Lean, Dev Trends, Chicago) each with their top headline, so the vitals panel can link out to today's research without re-parsing five files.
9. As a user, when a lane brief ran but found nothing today, I want that lane's `headline` to be `null` rather than an empty string, so the HUD can distinguish "nothing to report" from "not run yet" (the lane itself is present either way; only the file's existence gates that).
10. As a user, when a lane hasn't produced a file for today at all, I want that lane simply absent from the list, matching the existing Next.js behavior.
11. As the HUD, I want a median expected duration per skill, computed from real completed runs, so the task callout can show a progress estimate instead of a spinner with no ETA.
12. As a developer, I want skill ETAs computed from the `jobs` table (the reconciled source of truth since Stage 2), not by re-reading `system/runs/*.json` files directly, so this doesn't regress behind the reconciliation work that made the database authoritative.
13. As a user, I want only successfully-completed (`ok`) runs counted toward a skill's ETA, so a skill that mostly errors doesn't get an artificially low estimate from its few failures' short runtimes.
14. As the HUD, I want the composite's `queue` field to list only jobs still `queued` (not yet `running`), so a "waiting to start" indicator doesn't include jobs already in flight.
15. As the HUD, I want each queued job to carry the same `label` (voice-ask topic tag) as `/jobs` and `/runs` already do post-Stage-4, so the queue view and the active/history views render labels consistently.
16. As the HUD, I want every job and run response (`/jobs`, `/jobs/{id}`, `/runs`, `/runs/{id}`) to include a `label` field — a short topic tag derived from a voice-ask's prompt — so two simultaneous voice asks don't both render as indistinguishable "voice ask" entries.
17. As a user, I want `label` to be `null` for any non-`voice-ask` skill, so it's obvious the field only applies to that one skill.
18. As the HUD, I want a completed run's response to include `link` — an external URL parsed from the deliverable's frontmatter, when present — so a run whose real output lives elsewhere (a Gmail draft, a video) can be opened directly instead of showing an internal markdown path.
19. As a developer, I want `link` parsing reused from the exact path-allowlist and resolved-path guard Stage 3's code review already established for path-traversal safety, not a second implementation of that check, so there's one audited path-safety boundary, not two.
20. As a user, I want `link` to only ever be computed for a job whose status is `ok`, so a still-running or errored job never shows a stale or nonexistent deliverable link.
21. As the HUD, I want every job/run response to include `duration_s` — the run's wall-clock duration when both start and completion timestamps are known — so the history view can show how long a run actually took.
22. As a user, I want `duration_s` to be `null` when either timestamp is missing, rather than a misleading `0`, so an incomplete record doesn't look like an instant run.
23. As the HUD, I want `/runner`'s response to include `version`, `busy`, `max_concurrent`, and `heartbeat_age_s` alongside the existing fields, so the runner status panel can show load and freshness, not just alive/dead.
24. As a user, when the runner heartbeat file is missing entirely, I want the new fields to come back as explicit `null`/`false` in the "not reporting" shape, matching how the existing fields already degrade.
25. As the HUD, I want `/daily`'s response to include `top3` — the day's Top 3 Priorities, each with its text and done-state — so the priorities panel doesn't need a second endpoint.
26. As a developer, I want `top3` parsed from the note body's numbered checkboxes (`1. [ ] text` / `1. [x] text`) per the frozen `system/schemas/daily-note.md` parser rule, not from the frontmatter `top3`/`top3_done` arrays, so the read path matches the schema's documented source of truth rather than a write-side convenience cache.
27. As a user, I want an empty or not-yet-filled-in Top 3 item to still appear in the list (with empty text), so the panel can render three placeholder slots even before the user has filled them in.
28. As the HUD, I want `/state`'s embedded `daily` to always be today's note (in `HUD_TZ`), so the composite doesn't need a separate "which day is this" field.
29. As a developer, I want `/state` to compose by calling the same underlying functions each individual endpoint already calls, not by making internal HTTP requests to itself, so there's no self-request overhead or route-coupling.
30. As a developer, I want `/state`'s embedded `runs` capped to the HUD's historical window (8 entries), not the `/runs` endpoint's own default (50), so the composite matches what the cockpit actually renders without over-fetching.
31. As a user, I want `/state` to return a plain 503 (matching every other endpoint) when the vault root is unreadable, so a broken vault fails the same way everywhere instead of `/state` inventing a new partial-response behavior.
32. As an operator, I want a systemd `--user` unit for the spine, so it survives reboots and restarts on crash without a login shell holding it open.
33. As an operator, I want the spine's environment variables (`VAULT_ROOT`, `VAULTOS_DB`, `VAULTOS_PORT`, `TOKEN_BUDGET_5H_USD`, `HUD_TZ`) loaded from a file dedicated to this service, not `~/.claude/.env` (which `runner.js` already owns), so the two services' configuration doesn't get coupled.
34. As an operator, I want the unit's `ExecStart` to invoke the repo's own venv `uvicorn` binary directly, with no wrapper script, so there's one less moving part to debug when the service won't start.
35. As an operator, I want the service to restart automatically on failure, so a crash doesn't require someone to notice and manually restart it.
36. As an operator, I want the unit file committed in the repo (`deploy/vaultos-api.service`) with install steps documented as plain `systemctl --user` commands, so installing it doesn't require a script maintained separately from the unit file itself.
37. As a developer, I want the unit to skip sandboxing directives (`NoNewPrivileges`, `MemoryDenyWriteExecute`, etc.) for this stage, so an early crash surfaces as a real error rather than a permission failure masking the actual bug — hardening is revisited once the service has run stably for a while.
38. As a developer verifying this stage, I want a one-time manual diff of `/state` against the live Next.js `/api/state`, documented in the stage's PR, confirming every `VaultState` field has spine-side data behind it — not an automated test with a runtime dependency on a second repo's dev server.

## Implementation Decisions

- **`vaultos/vault/metrics.py`** gains a `LatestVideo` dataclass (`title`, `url`, `video_id`, `views`, `likes`, `comments`, `published_at`, `status`) and `read_latest_video(vault_root) -> LatestVideo | None`, parsing `system/metrics/latest-video.json` with the same safe-JSON-with-try/except pattern as `read_last_pull` in the same module. Lives here since this module already owns everything under `system/metrics/`.
- **New module `vaultos/vault/reports.py`**: a `Headline` dataclass (`text`, `link`) and `parse_headline_bullets(raw, max) -> list[Headline]` — a direct port of `Fable-Os-Web/lib/vault.ts`'s `parseHeadlineBullets`: finds a `## Headlines` section (case-insensitive), stops at the next `##` heading, collects `-`/`*` bullet lines, extracts the first `http(s)` URL on the line as `link`, strips markdown links/bare URLs/emphasis markers from the text, truncates to 160 chars.
  - `MorningReport` dataclass (`rel`, `headlines: list[Headline]`) and `read_morning_report(vault_root, tz, max=4) -> MorningReport | None`: finds today's (in `HUD_TZ`) file under `inbox/reports/morning/` by date-prefix, parses via `parse_headline_bullets`.
  - `LaneBriefItem` dataclass (`source`, `skill`, `title`, `rel`, `headline: str | None`) and `read_lane_briefs(vault_root, tz) -> list[LaneBriefItem]`: iterates the five known lanes (`leadership_brief`/`leadership-brief`/Leadership, `payments_brief`/`payments-brief`/Payments, `lean_brief`/`lean-brief`/Lean, `dev_trends_brief`/`dev-trends-brief`/Dev Trends, `chicago_brief`/`chicago-brief`/Chicago — ported from Next.js's `LANE_BRIEFS` constant), finds each lane's `{today}-{skill}-*.md` file under `inbox/research/` if present, parses just the first headline (`max=1`).
- **`vaultos/jobs/store.py`** gains `compute_skill_etas(conn, limit=200) -> dict[str, int]`: queries the `jobs` table for `status='ok'` rows with both `ts_started` and `ts_completed` set, most recent `limit` by `ts_completed`, groups by `skill`, returns the median `duration_s` per skill. Deliberately DB-sourced, not file-sourced — the `jobs` table is the reconciled source of truth since Stage 2; re-parsing `system/runs/*.json` directly here would bypass that.
- **`vaultos/api/jobs.py`**: `_job_to_dict()` gains three derived fields, extending `/jobs`, `/jobs/{id}`, `/runs`, and `/runs/{id}` uniformly (all four already share this function):
  - `label`: new helper `ask_label(args) -> str | None`, a direct port of the frontend's `askLabel()` (same stopword list) — only computed when `skill == "voice-ask"`, else `null`.
  - `link`: new helper `deliverable_link(vault_root, deliverable_path) -> str | None`, a port of `deliverableLink()` — reads the deliverable's frontmatter for a `link:` field, only called when `status == "ok"`. Reuses the exact allowlisted-prefix + resolved-path-must-start-with-vault-root guard Stage 3's code review already added for `/daily`'s path-traversal fix — the same audited boundary, not a second implementation.
  - `duration_s`: computed from `ts_started`/`ts_completed` when both are present, else `null`.
- **`vaultos/vault/runner.py`**: `RunnerHeartbeat` gains `version: str`, `busy: bool`, `max_concurrent: int`, `heartbeat_age_s: float | None` — the last of these is the `age` value `read_heartbeat()` already computes internally but currently discards; now returned. `vaultos/api/runner.py`'s response dict, and its "heartbeat file missing" fallback shape, both gain the four fields (the fallback shape returns explicit `null`/`false`).
- **`vaultos/vault/daily.py`**: `DailyNote` gains `top3: list[Top3Item]` (`Top3Item(text: str, done: bool)`), parsed from the body's `## Top 3 Priorities` section against `^\d+\.\s+\[([ x])\]\s+(.*)$`, per `system/schemas/daily-note.md`'s own parser rule — not the frontmatter `top3`/`top3_done` arrays, which the schema documents as a write-side index cache for the toggle-a-checkbox endpoint, not the read-side source of truth. `vaultos/api/daily.py`'s response gains `top3: [{text, done}, ...]`. No `is_today` field is added (see Out of Scope).
- **New router `vaultos/api/state.py`**, `GET /state`: assembles `generated_at` (request-time UTC timestamp), `vault_root`, `metrics`, `runner`, `latest_video`, `daily` (always resolved for `date=today`), `runs` (capped to 8, not `/runs`'s default 50), `queue` (jobs filtered to `status="queued"`, using the same augmented `_job_to_dict` shape as everywhere else — no separate lighter shape), `morning`, `skill_etas`, `lane_briefs` — by calling the same underlying `vault/*.py` functions and `store` queries every individual endpoint already calls, not by making internal HTTP requests to the spine's own routes. No `lane_highlights` key is present at all (not `null` — absent), per the original carve-out (design spec §5).
- **Router wiring**: `vaultos/main.py` gains one new `app.include_router(state.router)` call, same no-prefix pattern as every existing router.
- **Error handling**: `/state` follows the existing convention exactly — `HTTPException(503, ...)` when `settings.vault_readable()` is false, for the whole response. No new "degraded composite" behavior is invented for this stage.
- **JSON casing**: snake_case throughout, including `/state` and every new/extended field (`latest_video`, `skill_etas`, `lane_briefs`, `duration_s`, `heartbeat_age_s`, `max_concurrent`) — matching the decision recorded in ADR-0004.
- **systemd unit**: `deploy/vaultos-api.service`. `ExecStart` invokes `<repo>/.venv/bin/uvicorn vaultos.main:app --host 0.0.0.0 --port 3109` directly (no `--reload`, no wrapper script). `EnvironmentFile=` points at a dedicated, gitignored env file at `~/.config/vaultos-api/env` (XDG-conventional, not `~/.claude/.env`) holding `VAULT_ROOT`, and optionally `VAULTOS_DB`/`VAULTOS_PORT`/`TOKEN_BUDGET_5H_USD`/`HUD_TZ` when overriding their defaults. `Restart=on-failure`, `RestartSec=1` (matching `syncthing.service`'s cadence, without adopting its hardening directives). `WantedBy=default.target`, installed via documented manual `systemctl --user daemon-reload && systemctl --user enable --now vaultos-api.service` steps in a short runbook (README section or `deploy/README.md`) — no install script. No `NoNewPrivileges`/`MemoryDenyWriteExecute`/etc. hardening this stage.

**Update 2026-08-10 — `latest_video` retired.** Every `latest_video`/`LatestVideo`/`read_latest_video` reference documented above (the `/state` field, the `vault/metrics.py` dataclass and reader, the snake_case field list, and the corresponding test file) has been removed from the codebase. The user has no YouTube account — this was never a real data source (`metrics.csv` never had YouTube rows), and the feature is cancelled rather than left as a pending gap. See ADR-0008's update note.

## Testing Decisions

Good tests here exercise only external behavior — what a `vault/*.py` function returns for a given fixture, what a `store` query returns for given DB rows, what a given HTTP call returns — never internal implementation details. Matches Stages 1-3's existing style: real `tmp_path`/`tmp_vault`/DB fixtures, zero mocks.

- `vault/metrics.py`'s `read_latest_video`, `vault/reports.py`'s `read_morning_report`/`read_lane_briefs`, and `vault/daily.py`'s `top3` parsing: tested directly against `tmp_vault`-style fixtures, no HTTP. Prior art: `tests/test_vault_daily.py`, `tests/test_vault_metrics.py`.
- `store.compute_skill_etas`: tested directly against a real sqlite connection with fixture job rows inserted (mixed `ok`/`error` statuses, some missing timestamps). Prior art: `tests/test_jobs_store.py`.
- `ask_label` and `deliverable_link`: focused unit tests isolated from HTTP and the filesystem where possible — synthetic `args` dicts for `ask_label`; a `tmp_vault` fixture with a deliverable file for `deliverable_link`. Prior art: Stage 3's isolated token-burn-projection unit test.
- **Path-traversal regression test for `deliverable_link`**: extends the exact pattern Stage 3's code review added for `/daily` (`tests/test_api_daily_security.py`) — a `deliverable_path` containing `../` must not escape the vault root, asserted directly against `deliverable_link()`.
- Extended endpoints (`/daily`, `/runs`, `/jobs`, `/runner`) and the new `/state`: FastAPI `TestClient`, same seam as every existing endpoint test. Prior art: `tests/test_api_daily.py`, `tests/test_api_runs.py` (if present) or `tests/test_api_jobs.py`.
- **Parser fixtures copied from the real vault**: a real (trimmed) daily note with the actual frontmatter-plus-body Top 3 shape, a real morning report file, and real lane-brief files — kept as permanent regression fixtures, same convention Stages 2-3 established.
- **`/state` completeness check**: not automated (no cross-repo runtime dependency on a live Next.js dev server) — a one-time manual diff against the live Next.js `/api/state`, documented as a check-off in the stage 4 PR, confirming every `VaultState` field has spine-side data behind it. See the design spec's updated §9.

## Out of Scope

- Byte-for-byte `VaultState` JSON parity for `/state` — deliberately not the goal; see ADR-0004.
- `is_today` on `/daily` — not added. `/state` always requests `date=today`, and the spine's `/daily` never falls back to a different day the way Next.js's reader does (an already-settled Stage 3 behavior: `exists=False` for an unwritten note, no silent fallback to the most recent prior note). Within `/state`, "today" is always today by construction, so a persisted field would be redundant.
- Reading the frontmatter `top3`/`top3_done` arrays as the source of truth for `top3` — deliberately not used; the frozen schema documents body-section parsing as the read path (see Implementation Decisions).
- `laneHighlights` — stays computed in `Fable-Os-Web`'s Next.js layer; its permanent home is a sub-project 2 decision, unchanged from the original carve-out (design spec §5).
- Fixing `Fable-Os-Web/lib/vault.ts`'s `readDailyNote()` reading `## Current Focus`'s body text instead of the frontmatter `focus` field the schema and the spine both treat as canonical (see Further Notes) — that's Next.js code, out of scope for a spine-only spec.
- Any caching layer for the new reads — re-read per request, same as Stages 1-3's stance; revisit only if it becomes a real problem.
- systemd install automation or a provisioning script — manual documented `systemctl --user` steps only (Q6 of the grilling round).
- Sandboxing/hardening directives on the unit (`NoNewPrivileges`, `MemoryDenyWriteExecute`, `SystemCallArchitectures=native`, etc.) — deferred until the service has run stably for a while (Q7).
- Actually deleting `/state` — happens later, once sub-project 2's HUD cutover lands (design spec §5), not part of this stage.
- Per-source staleness refinement for `/integrations`, token-burn rate-limit anchoring — already out of scope from Stage 3 (ADR-0002, ADR-0003), not re-litigated here.

## Further Notes

- **A real staleness finding, not a spine bug**: `Fable-Os-Web/lib/vault.ts`'s `readDailyNote()` reads `## Current Focus`'s body text for `focus`, but `system/schemas/daily-note.md` (frozen) and the spine's own `vault/daily.py` both treat frontmatter's `focus:` field as canonical — and current daily notes carry an empty `## Current Focus` body while the real value lives in frontmatter. This means the live Next.js `/api/state`'s `focus` field is likely already blank/stale, independent of anything built in this stage. Worth knowing during the Q4 manual parity diff: a `focus` mismatch there reflects Next.js's own staleness, not a spine defect. Not fixed here — it's a different repo's code, and this spec is spine-only.
- `top3`, by contrast, checked out consistent: the current schema's body-section checkbox format is exactly what Next.js already parses, and a real daily note file confirms both the frontmatter arrays and the body checkboxes are present and in sync (both empty today). No contradiction there.
- `docs/adr/0004-state-uses-spine-shape-not-vaultstate-parity.md` and the design spec's updated §5/§9 are already committed on branch `worktree-vault-os-api-stage4-grill` — read alongside this spec, not duplicated into it.
- None of the new fields (`latest_video`, `morning`, `skill_etas`, `lane_briefs`) introduce new domain vocabulary requiring a `CONTEXT.md` entry — each is a direct, unambiguous port of an already-established Next.js concept with a stable, uncontested meaning.
